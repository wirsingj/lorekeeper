# yaiml-refresh

Read [Using YAIML](../../YAIML_GUIDE.md) for shared context, evidence, authority and retention rules; reuse it and current core memory if already loaded. “Update YAIML”, “check new YAIML” and re-init select this method; “update our SoT” selects `yaiml-maintain`. Reuse current local guidance during ordinary work; do not poll upstream at startup.

First establish the target's role from its own instructions. In the project developing YAIML, “update YAIML” means improve canonical guidance within the requested scope and maintain affected project memory; follow its contributor procedures instead of applying an adopter refresh over authored sources. Having copied YAIML methods alone does not establish that role. The remaining acquisition steps apply to adopting projects; source-project Git synchronization requires its own authorized Git scope.

For adopter refresh, default to the latest `main` of https://github.com/wirsingj/YAIML. Another source requires an explicit user request within its stated scope; a recorded source or workspace checkout alone is not an override. Preserve prior source notes for provenance and comparison. Resolve `main` anew for each refresh and use that exact commit throughout this acquisition; prompt stamps and previous source notes are not pins. Honor an explicitly requested source/ref, resolving an alternative repository's default branch once if no ref was specified, or identifying the requested snapshot. If access fails, retain working guidance and report the gap rather than substituting a source. Inspect worktree, source notes and installed routes before writes. Identify incoming revision/snapshot, material reference edits, local adaptations and any unavailable prior base. Read incoming `.yaiml/BOOTSTRAP.md` at that same revision before enumerating resources; a legacy copy cannot define the new package completely. Follow its resource list, references and transition procedure. Discovery version describes layout, not content freshness. Read the incoming release and [revision guidance](../../VERSIONING.md), retrieving them through that source if absent locally; compare release identity separately from local counters and applied source commits.

Before the first write, retain enough of the permitted pre-update file state or change inventory to verify the final diff through partial failures. Do not reset that comparison baseline after a blocked route write or interrupted step.

For each affected upstream-owned method/source, compare incoming guidance with the previously applied revision and current local file where available. Apply compatible changes in focused passages, preserving project facts, custom skills, names, headers, budgets, retention and stricter local authority. If the base is unavailable, make conservative semantic comparisons and disclose uncertainty. Preserve unknown extensions and conflicting decisions; block only dependent changes. Never replace a whole mature memory family with templates.

Repair missing/reachable bodies, notices, catalogs and host routes together. Handle upstream renames/removals by checking local callers and value; preserve adapted useful methods until their replacement is reconciled. Consolidate equivalent old YAIML boilerplate into the incoming shared-guide route, preserving unique project constraints, stricter local rules and unresolved differences. Apply the acquired transition in this update session: establish the core changes role and prospective revision baseline when missing, retaining existing records, labels and layout. Do not stop at copying the new instructions. Never import the source project's audit or treat upstream file counters as local progress. Update the existing source note only for applied resources; retain per-resource revision exceptions or unresolved differences instead of claiming everything updated. Apply [the record transition](../../CHANGE_RECORDS.md#transition-and-recovery), preserving pending records, receipts, inline history and stricter local rules. Retire obsolete mode switches only after reconciling their meaning; do not erase or silently incorporate pending work. An unchanged repeat run leaves healthy files unchanged.

For requested relocation, use Bootstrap's existing-layout procedure. Re-init offers consolidation but no answer preserves paths while refresh continues. No discovery migration, application work or delegation is implied. Check exact paths with actual consumers; quote numeric version labels without changing their spelling. Report applied/unchanged/partial/conflicting results and actual checks. Maintain project memory only for changed understanding.
